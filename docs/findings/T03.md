# T03 findings: printing Chinese A4 with Browser Rendering + Paged.js

Experiment for T07 (print service) and T08 (ground truth). Date: 2026-10-23/24.

Every claim below names its evidence. **E:** paths are files in `spike/t03/evidence/` at commit `d9eb0b7` of branch `t03-print-spike` (visible in the T03 PR's commits; the merge itself contains only this file). The spike code is in the same commit (`spike/t03/src/index.ts`, `public/probe.js`, `scripts/*.mjs`).

## Rules for T07 and T08

These follow from the findings below. The section that backs each rule is given in brackets.

**Must**

1. Read `data-gt` boxes only after Paged.js has finished. Use `window.PagedConfig.after` (or a flag it sets that puppeteer waits on with `waitForFunction`). [§3]
2. Make every box relative to its `.pagedjs_page` element's `getBoundingClientRect()` and convert CSS px to PDF pt with × 0.75. Take the page number from the page's position in `.pagedjs_page` order. [§3, §4]
3. Read the boxes in the same browser session, on the same page, that prints the PDF. Layout differs between Chrome versions. [§5, §6]
4. After pagination, fail the render if any text node has a client rect outside its page's `.pagedjs_page_content` rect. Paged.js 0.4.3 can silently drop a table row, and this check catches it. [§5]
5. After pagination, fail the render if any `document.fonts` face is not `loaded`. Paged.js only logs a warning. [§2.4]
6. In the self-check, compare the PDF's embedded font names against the pack's fonts. Treat any other font as an error: it means a glyph fell back to a system font. [§2.3]
7. Use fonts whose cmap has no shared radical/compatibility code points (the patch in §2.5), or expect the PDF text layer to differ from the source text. [§2.5]
8. Declare in `@font-face` only the faces a document actually uses. Paged.js downloads every declared face before it paginates. [§2.4]

**Must not**

1. Don't read coordinates at `DOMContentLoaded`, `load`, `document.fonts.ready`, `networkidle`, or when the first `.pagedjs_page` appears. [§3]
2. Don't rely on Paged.js 0.4.3 to repeat `<thead>` on the next page, or to keep table column widths the same across pages. [§5]
3. Don't push fonts (or other large assets) to the browser through puppeteer request interception from the Worker. 3 of 4 such requests on the real platform ended in error 1102. [§6.3]
4. Don't treat local `wrangler dev` (Chrome 126) or a local Playwright Chromium as equal to Browser Rendering (Chrome 152) for layout. [§5, §6]
5. Don't call `puppeteer.connect` to a session right after another Worker request disconnected from it, without retrying. 2 of 3 immediate reconnects failed with "may still be in use". [§6.4]

## 1. Setup

- Spike Worker: `@cloudflare/puppeteer` 1.4.0, `pagedjs` 0.4.3 (`paged.polyfill.js`), wrangler 4.152.0. It loads a fixed document, waits for Paged.js, reads boxes and prints with `page.pdf({ preferCSSPageSize: true, printBackground: true })`.
- Test document (`scripts/make-doc.mjs`): A4, `@page` margins 20/18/22/18 mm, a page-counter footer, 26 `data-gt` blocks (title, headings, paragraphs, rare characters, punctuation, a serif and a kai paragraph), a 45-row table with `<thead>` that crosses a page, and a forced page break. Output: 4 pages.
- PDF analysis (`scripts/analyze.mjs`): pdf.js 6.4.299 extracts the text items with font names. Each item is assigned to the block whose box contains its anchor point (horizontal centre, 0.35 em above the baseline). The script then compares texts and positions.
- Browsers: **local** = the `wrangler dev` local Browser Rendering binding, Chrome/126.0.6478.182 (E: `local-bench.txt`). **remote** = real Browser Rendering, Chrome/152.0.7977.64 (E: `remote-summary.json` → `launch.version`, `runBadFont.browserVersion`). **preview** = the T3 preview browser, Chrome/154.0.0.0 (E: `preview-chrome154.json`).

## 2. Fonts

### 2.1 Replacements for Word's Chinese fonts

| Word font | Free replacement | Licence | File used |
| --- | --- | --- | --- |
| 微軟正黑體 (sans) | Noto Sans TC 2.004 | SIL OFL 1.1 | `NotoSansTC-{Regular,Bold}.otf` (noto-cjk `Sans/SubsetOTF/TC`) |
| 新細明體 (serif / 明體) | Noto Serif TC 2.003 | SIL OFL 1.1 | `NotoSerifTC-{Regular,Bold}.otf` (noto-cjk `Serif/SubsetOTF/TC`) |
| 標楷體 (kai) | LXGW WenKai TC 1.530 | SIL OFL 1.1 | `LXGWWenKaiTC-Regular.ttf` |
| (☑ ☐ and other symbols) | Noto Sans Symbols 2 2.008 | SIL OFL 1.1 | `NotoSansSymbols2-Regular.ttf` |

E: `fonts.txt` (source URLs, sha256, sizes, versions, copyright lines). None of the three licence files declares a Reserved Font Name (`grep -i "with reserved font name"` finds nothing; Noto Sans and Serif share one identical licence file; E: `fonts.txt`), so a cmap-patched copy (§2.5) may keep its name under OFL 1.1. All four fonts have OS/2 `fsType` with no embedding or subsetting restriction (E: `fonts.txt`).

The OFL lets us bundle and embed these fonts. T07 should ship the licence text with the fonts.

### 2.2 Embedding

Fonts were declared with `@font-face` and loaded from the Worker's static assets. Chrome embeds each used face as a subset (names like `AAAAAA+NotoSansTC-Regular`, E: `run-fixed.analysis.json` → `summary.fonts`). The 4-page document produced a 460,197-byte PDF locally and a 501,489-byte PDF remotely (URL mode, E: `remote-summary.json` → `benchTabs3Url.pdfBytes`). File sizes: Sans 5.7–5.8 MB, Serif 7.9–8.3 MB, WenKai 15.3 MB per face (E: `fonts.txt`).

### 2.3 Coverage gaps: "no missing glyphs" holds only for covered characters

With stock fonts (run-local), the PDF's fonts were: Noto Sans TC Regular/Bold, Noto Serif TC, LXGW WenKai TC, plus fallbacks `WenQuanYiZenHei` (1 char: 㵾), `IPAGothic` (1 char: 𩸽) and `DejaVuSans` (44 chars: every ☑/☐) (E: `run-local.analysis.json` → `summary.fonts`). fontkit confirms that Noto Sans/Serif TC have no glyph for ☑ ☐ 㵾 𩸽 but do have 𡘙 𠀾. LXGW WenKai TC has ☑ ☐ 𩸽 but not 㵾. Noto Sans Symbols 2 has ☑ ☐ (E: `fonts.txt`).

With Noto Sans Symbols 2 added to the font-family list, ☑ ☐ were embedded from it (44 chars, E: `run-fixed.analysis.json`). 㵾 and 𩸽 still fell back to system fonts.

Consequences:
- In these runs the PDF showed no tofu, because Chrome silently substituted a system font that had the glyph. So "no missing characters" must be checked by font name in the PDF (rule M6), not visually.
- Browser Rendering ships Noto Sans CJK TC. When the web font failed remotely, the whole text was printed in `NotoSansCJKtc-Regular/Bold`, which looks almost identical to Noto Sans TC (E: `remote-run-badfont.analysis.json` → `summary.fonts`). A failed font load is therefore easy to miss by eye.
- The fake-data engine (T05) should draw only characters the pack's fonts cover, or the self-check will fail. Proposal, not tested: compute the covered set from the font's cmap.

### 2.4 Font loading and Paged.js

- Paged.js runs `loadFonts()` before laying out. It calls `.load()` on every `document.fonts` face whose status is not `loaded`, including faces no element uses. A failure only produces `console.warn("Failed to preload font-family: …")` (source: `paged.polyfill.js` 0.4.3, lines 3280–3296). Observed: in the broken-font run, the page used only the missing family `Broken TC`, yet all 6 declared faces (≈44 MB) were fetched, remotely as well (E: `remote-summary.json` → `runBadFont.fetched`).
- With a family whose only source returned 404, Paged.js still finished (`done: true`, 4 pages). The face's status was `error`, and the PDF was printed in fallback fonts (local: WenQuanYi Zen Hei, Liberation Serif, DejaVu Sans; remote: Noto Sans CJK TC, DejaVu Sans) (E: `run-badfont.analysis.json`, `remote-run-badfont.analysis.json`, `local-runs.json` → `run-badfont.paged.faces`).

### 2.5 Selectable text: the PDF text layer differs from the source unless the fonts are patched

The PDF text is selectable and extractable (pdf.js returns text for every block). With stock Noto fonts, though, 25 of 27 block fragments did not match the source text. Common characters came out as Kangxi radicals or CJK radical-supplement code points: `一`→`⼀` U+2F00, `月`→`⽉`, `人`→`⼈`, `門`→`⾨`, `長`→`⻑`, `頁`→`⾴` (E: `run-local.analysis.json` → `detail.pagedAfter.diffs`, `text-layer.txt`). NFKC normalisation fixes most of these but not all (7 blocks still differ).

Cause: Noto Sans TC maps several code points to one glyph (e.g. U+2F00 and U+4E00), and the PDF's ToUnicode entry for that glyph takes one of them. In every case observed it was the lowest code point: U+2F00 < U+4E00, U+2329 < U+3008, U+301C < U+FF5E. In stock Noto Sans TC Regular, 427 glyphs are reachable from more than one code point; after the patch below, 86 remain (E: `text-layer.txt` lists them). This rule is inferred from those observations; I did not read Chrome's source for it.

Fix tested: `scripts/fix-cmap.mjs` rewrites the cmap (one format-12 subtable). It drops code points in U+2E80–2FDF, U+F900–FAFF and U+2F800–2FA1F when their glyph is shared with another code point, and also drops U+2329, U+232A and U+301C. Glyph data is untouched (glyph count unchanged; 351 code points dropped for Sans, 358 for Serif; E: `fonts.txt`). With the patched fonts, 25 of 27 fragments matched exactly (E: `run-fixed.analysis.json` → `summary.snapshots.pagedAfter.textMismatch` = 2). The two left:
- `——` (two U+2014) is shaped into one glyph (id 1099) by a feature that `-liga`/`-clig`/`-dlig` does not turn off. It extracts as U+0000. With `font-feature-settings: "ccmp" 0` it extracted as `――` (U+2015 ×2), which is still wrong (E: `text-layer.txt`; that run used the first patch version, without the U+2329/U+232A/U+301C drops, which is why it also shows `〈〉〜`). Not solved. T05 should avoid `——`, or the self-check should map U+0000/U+2015 back.
- b21: the lost table row (§5).

The patch also fixed the page-counter footer (`第 1 ⾴` → `第 1 頁`; E: `run-fixed.analysis.json` → `detail.pagedAfter.unmatchedItems`).

Not checked: the full set of shared glyphs in Noto Serif TC and LXGW WenKai TC beyond the radical ranges. The kai paragraph (b19) matched exactly in both the stock and the patched local runs (E: `run-local.analysis.json`, `run-fixed.analysis.json` → `detail.pagedAfter.rows`).

## 3. When Paged.js is finished: the exact signal

Paged.js's polyfill runs `await config.before()`, then `await previewer.preview()`, then `await config.after(flow)` (source: `paged.polyfill.js` lines 33221–33248). `preview()` returns only after the chunker has rendered every page, run the `afterRendered` hooks and the `afterPreview` hook (lines 2918–2935, 33157–33190). So `PagedConfig.after` runs after the last page exists.

What the spike does (`public/probe.js`): it sets `window.PagedConfig = { auto: true, before: async () => { await document.fonts.ready }, after: (flow) => { window.__t03 = { done: true, total: flow.total, … } } }` before loading `paged.polyfill.js`. The Worker then calls `page.waitForFunction(() => window.__t03.done === true)`.

Boxes recorded at each moment, compared with the printed PDF (local, E: `run-local.analysis.json`, `run-fixed.analysis.json` → `summary.snapshots`; remote, E: `remote-run-badfont.analysis.json`):

| Moment | `.pagedjs_page` count | Usable? |
| --- | --- | --- |
| `DOMContentLoaded`, `load`, `document.fonts.ready`, `PagedConfig.before` | 0 (pre-pagination layout; no PDF text matched) | no |
| puppeteer `goto(…, { waitUntil: 'load' })` returned | 0, `done=false` (local and remote) | no |
| puppeteer `waitForSelector('.pagedjs_page')` returned | local: 3 of 4, `done=false`; remote: 4 of 4, `done=true` | no: racy |
| `PagedConfig.after` | 4 of 4 | **yes** |
| puppeteer, after waiting on the `done` flag (screen media) | 4 of 4, identical to `after` | **yes** |
| same, after `page.emulateMediaType('print')` | 4 of 4, same positions | yes (no gain) |

In all 23 local `/run` outputs, the `after` reading and the post-flag reading were identical (`JSON.stringify` equal, boxes and line rects). The print-media reading had identical element boxes in all 23. Its line rects differed only by 4 exact duplicates of the `<thead>` cell rects on page 2 (21 runs) or not at all (2 runs) (E: `timing-consistency.txt`). `page.pdf()` printed the same pages Paged.js laid out: PDF page count = `flow.total` = 4 in every run (E: all `*.analysis.json` → `summary.pdfPages`/`pagedTotal`).

Timings (from `paged.log`, ms since probe start): Paged.js took 2.1–3.8 s locally (`beforePaged` → `pagedAfter`) and 21.3 s remotely in the one remote single run, which loaded 6 fonts by interception (E: `local-runs.json`, `remote-summary.json` → `runBadFont.paged.log`).

## 4. Coordinates match the PDF

Method: for each block fragment, the DOM line rects (`Range.getClientRects()` on its text nodes, relative to its `.pagedjs_page`, × 0.75) are compared with the PDF text items assigned to it (§1).

- Horizontal: the left and right edges of the text agree within **0.01 pt** in all four analysed runs (local stock fonts, local patched fonts, local fallback fonts, remote fallback fonts; E: `*.analysis.json` → `summary.snapshots.pagedAfter.maxDevXPt`).
- Vertical: every assigned PDF text run's baseline lies inside one of its block's DOM line boxes (`baselineOutside` = 0 of 620, 283, 373 and 644 matched items; E: same files). Using each font's ascent/descent as pdf.js reports it (Noto Sans TC: 1.16 / −0.288 em), the top and bottom edges also agree within 0.53 pt for all 25 non-table block fragments, the WenKai paragraph included (E: `run-fixed.analysis.json` → `detail.pagedAfter.rows`; the 3.03 pt on the page-3 table fragment comes from the ☐ glyph of Noto Sans Symbols 2: pdf.js reports its descent as 0.63 em, and it sits on the same baseline, 603.00, as the rest of the row; E: `table-bottom-glyphs.txt`).
- The page-2 table fragment is the exception (deviation 21.97–25.39 pt): its DOM rects include the lost row in the hidden overflow column (§5).
- Visual check: `local-page1-boxes.png` shows the red `data-gt` boxes and blue line rects drawn by `public/viewer.html` (pdf.js rendering of the printed PDF) over the glyphs of page 1.

Not covered: rotated text, vertical writing, images, and `data-gt` elements without text. The block box itself (`getBoundingClientRect` of the element, including padding) was not compared, only its text lines.

## 5. Paged.js 0.4.3 table defects

**Lost row.** In the local runs (Chrome 126), row 023 of the table started 15.6 pt above the bottom of page 2's content area and needed 25.2 pt. Paged.js left it on page 2, fragmented into the content area's hidden overflow column: each cell has 2 client rects and the row's rect reaches x = 1889 pt. Page 3 starts at row 024, so row 023 is in no page of the PDF (E: `local-runs.json` → `run-local.rowsNear`, `rows-in-pdf.txt`, screenshot `local-page2-lost-row.png`: no glyphs after row 022, and the blue DOM rects of row 023 below the table).

| Extra `margin-top` on the table | Space left after the last row that fits | Row lost? | Overflow guard |
| --- | --- | --- | --- |
| 0 pt | 15.61 pt | yes (023) | 4 text nodes flagged |
| 10 pt | 14.11 pt | yes (023) | 4 flagged |
| 12 pt | 2.87 pt | no | none |
| 16 pt | 8.11 pt | no (023 moved to page 3; an empty row shell stays on page 2) | none |
| 24 pt | 0.11 pt | no | none |

E: `local-runs.json` (`sweep-*`), `rows-in-pdf.txt`. Also tried, all still losing a row at 0 pt: `tr { break-inside: avoid }`, `td, th { break-inside: avoid }`, `border-collapse: separate`, cell padding 0 (E: `local-runs.json` → `run-avoid`; the other three variants were checked the same way, but their JSON is only in the spike's gitignored `out/`). In the T3 preview's Chrome 154 the same document put row 023 on page 3, with rows 24.87 pt tall instead of 25.22 pt (E: `preview-chrome154.json`). On remote Chrome 152 with fallback fonts no row was lost (45 of 45 in the PDF; E: `rows-in-pdf.txt`). Whether a row is lost therefore depends on the exact layout. The overflow guard (`window.__t03overflow` in `probe.js`) flagged exactly the lost cases and nothing else in these runs.

**No repeated header.** Paged.js 0.4.3 has no `<thead>` repetition: its source references `THEAD` only to honour `break-inside: avoid` on a row's parent (lines 1949–1953). Page 3 of the table starts with a body row both locally and remotely (E: `table-columns.json` → `byPage.3.firstRow`). T07's acceptance ("跨頁表頭有重複") needs its own handler.

**Column widths change per page.** The table's continuation on page 3 is laid out again with auto widths: column 2 starts at x = 121.58 pt on page 2 and 116.86 pt on page 3 (local and remote alike; E: `table-columns.json`). Proposal, not tested: `table-layout: fixed` with explicit column widths.

## 6. Browser Rendering on the real account

One approved batch on 2026-10-24, with Worker `t03-print-spike` deployed and then deleted (the URL returned 404 afterwards). Renders: at most 28 (12 + 12 bench, ≤3 single runs, ≤1 reuse). Browser launches: 6. E: `remote-summary.json`.

### 6.1 Limits (`puppeteer.limits()`)

`maxConcurrentSessions: 200`, `allowedBrowserAcquisitions: 10`, `timeUntilNextAllowedBrowserAcquisition: 0`, before and after the batch (E: `remote-summary.json` → `limitsBefore`, `limitsAfter`). The account is therefore on Workers Paid. Cloudflare's limits page (updated 2026-10-14) lists for Paid: 200 concurrent browsers, 3 new browser instances per second, 60 s default inactivity timeout, `keep_alive` max 20 min. For Free: 3 concurrent browsers, 1 new instance every 20 s, 10 browser-minutes per day. The batch only checked the 200 figure and the timeout (§6.4). Starting 3 browsers at the same moment caused no rejection.

### 6.2 Launch latency

Observed `puppeteer.launch` times: 88.5 s (first launch of the batch), 38.0 / 38.2 / 38.8 s (three concurrent), 3.3 s (last). One `/limits` call right after the deploy took 277 s to answer. One sample each; I don't know the cause (E: `remote-summary.json` → `launch.launchMs`, `benchBrowsers3Url.lanes`, `reuse75s.launchMs`). Plan for launches taking tens of seconds: launch once per batch, then reuse the browser and its tabs.

### 6.3 Throughput (4-page A4 document, fonts loaded by URL)

| Run | PDFs | Wall time | PDFs per minute | Per render |
| --- | --- | --- | --- | --- |
| 1 browser (already running), 3 tabs × 4 | 12 | 52.7 s | **13.7** | first render per tab 33.5 / 11.6 / 8.2 s, later renders 6.0–6.4 s |
| 3 browsers launched in the request, 1 tab × 4 each | 12 | 67.4 s (≈38 s of it launching) | **10.7** | 2.3–8.8 s |

E: `remote-summary.json` → `benchTabs3Url`, `benchBrowsers3Url`. Every render returned 4 pages, a 501,489-byte PDF, and no overflow hits.

What the figures mean: measured end to end, one Worker request produced 10.7–13.7 PDFs per minute. Without the launch and the cold first render, the per-render times above suggest about 25–29 PDFs per minute per request with 3 tabs or 3 browsers. That is derived, not measured over a full minute. Each figure comes from a single run.

**Interception fails remotely.** The spike's default mode answers every browser request, fonts included, from the Worker through `page.setRequestInterception`. 3 of the 4 remote requests in that mode ended in HTTP 503 with Cloudflare error **1102 (Worker exceeded resource limits)** after 41–52 s: `/run` with the patched fonts, `/run` with the stock fonts, and `/reuse` (E: `remote-summary.json` → `runFixed`, `runOrig`, `reuse5s` raw `"error code: 1102"`). The one that succeeded (the broken-font run) took 31.2 s. Whether CPU time or memory ran out was not determined (no `wrangler tail` in the batch). Locally, interception cost 4.6–7.4 s per render, against 2.6 s for the first and 1.1 s for later renders with URL loading (warm browser cache) (E: `local-bench.txt`). In URL mode the browser fetches the document and fonts itself and caches them. That needs a URL the browser can reach: T07 has to serve them on a path the browser can load without the Access login (T09). Not tested here.

The two single-browser benches by interception and by URL (10 renders each) did not run: their `puppeteer.connect` failed (§6.4). So there is no remote figure for sequential renders in one tab.

### 6.4 Sessions and timeouts

- Reconnecting to a kept-alive session (`keep_alive: 600000`) right after the previous request disconnected failed twice in a row with "Unable to connect to existing session … (it may still be in use or not ready yet)". The next request, about a second later, connected. So did `/close`, after the 53 s bench (E: `remote-batch.log` for order and durations; `remote-summary.json` → `benchSeqIntercept`, `benchSeqUrl`, `benchTabs3Url`, `close`). Why the first two failed is unknown.
- Idle timeout: a session launched without `keep_alive`, disconnected and left idle for 75 s could not be reconnected. `/limits` straight afterwards listed no sessions (E: `remote-summary.json` → `reuse75s`, `limitsAfter`). This is consistent with the documented 60 s default.
- The reconnect-after-5 s test did not reach the reconnect: its first render used interception and hit 1102 (E: `reuse5s`).

## 7. Local development notes (for T07/T08 in this VM)

- wrangler 4.152's local Browser Rendering binding works in the dev container, with two settings: `CI=1`, so miniflare starts Chrome with `--no-sandbox` (without it: "No usable sandbox!"), and a writable `XDG_CACHE_HOME`, because `~/.cache` is root-owned and Chrome downloads to `$XDG_CACHE_HOME/.wrangler/chrome` (observed in the dev-server log; miniflare source `ensureBrowserInstalled`, launch args `process.env.CI ? [...launchArgs, "--no-sandbox"]`).
- The local binding runs Chrome 126.0.6478.182, which lays out differently from the remote Chrome 152 (§5). T08's acceptance uses local Playwright: its gt.json can only be compared with PDFs printed by that same browser.
- The T3 preview browser does not display PDFs (it downloads them). `public/viewer.html` (pdf.js rendering plus box overlay) was used for the visual checks.

## 8. Open questions and inconclusive points

- Why interception hits 1102 (CPU or memory), and whether smaller font subsets would avoid it.
- A remote coordinate check with the bundled web fonts: both remote runs with them hit 1102. Remotely, only the fallback-font run was compared (§4).
- Remote throughput for one sequential tab, and more than one sample per configuration.
- Byte-identical PDFs for the same input: only equal sizes were observed (501,489 bytes across 24 remote renders), no hashes.
- A fix for the lost row and for `<thead>` repetition (a Paged.js handler, or another pagination approach) belongs to T07.
- `——` text extraction (§2.5).
